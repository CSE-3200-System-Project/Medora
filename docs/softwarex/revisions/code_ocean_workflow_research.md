# Code Ocean workflow for the SoftwareX revision

Checked against Code Ocean’s official documentation on 2026-09-23. The platform UI and journal integrations can change; confirm the intended peer-review route with the SoftwareX editor before submitting.

## Repo-specific findings

- Code Ocean’s GitHub importer recognizes root-level `metadata/`, `environment/`, `code/`, and `data/` folders. If these folders are absent, imported files land in “Other Files” and must be reorganized. This repo currently has a root `data/`, but its metadata is nested at `codeocean/metadata/metadata.yml`; it has no root `code/`, `metadata/`, or `environment/`. Therefore, cloning the repo as-is will not automatically place the run script and project sources under `/code` or use the nested metadata file. Prepare a capsule-specific folder layout or explicitly reorganize the imported files. Review what the root `data/` folder contains before importing it; the project’s [existing capsule note](../CODE_OCEAN_CAPSULE.md) records the unresolved medicine-corpus redistribution hold. [GitHub import guide](https://docs.codeocean.com/user-guide/v4.2.0/git-provider-integration-guide/github-integration-user-guide)
- Code Ocean’s metadata editor stores the capsule title, research field, description, authors, and tags in `/metadata/metadata.yml`; `/metadata` is not available during a Reproducible Run. The repo’s current `codeocean/metadata/metadata.yml` contains the name, authors, affiliations, and corresponding contributor, but not research field, description, or tags. Fill/confirm those fields in the capsule metadata editor. [Metadata guide](https://docs.codeocean.com/user-guide/v4.0.0/compute-capsule-basics/structure-of-a-compute-capsule/metadata) [Reproducible Runs guide](https://docs.codeocean.com/user-guide/v4.0.0/compute-capsule-basics/reproducible-runs)
- The Environment Editor configures the starter environment, compute resources, packages, environment variables, and optional `postInstall`; `/environment` itself is not mounted in the run. This repo’s root [`run`](../../../run) delegates to [`run_softwarex_capsule.sh`](../../../tools/release/run_softwarex_capsule.sh), which currently installs Python requirements at run time. Configure/verify the pinned Python environment in Code Ocean and test whether the runtime install succeeds there; do not rely on live service credentials. [Environment guide](https://docs.codeocean.com/user-guide/compute-capsule-basics/structure-of-a-compute-capsule/environment)
- A Reproducible Run executes the configured Bash `run` headlessly, starts in `/code`, exposes data at `/data`, and collects generated files from `/results`. The current runner writes fixture-test XML, copies the frozen safety/booking reports, regenerates TeX tables, and creates a hash manifest. Its successful run demonstrates that this defined workflow executes; it does not itself revalidate the article’s scientific claims or turn reused development fixtures into held-out evidence. Code Ocean explicitly describes its verification as mechanical reproducibility, not checking that capsule results match the article. [Reproducible Runs guide](https://docs.codeocean.com/user-guide/v4.0.0/compute-capsule-basics/reproducible-runs) [Verification checklist](https://docs.codeocean.com/osl-guide/publishing-on-code-ocean/the-verification-process/code-oceans-verification-process-for-computational-reproducibility-and-quality)

## Author-side order and handoff

1. Sign in/create the author-owned capsule, and confirm with the editor whether SoftwareX expects a Code Ocean peer-review copy or a public published capsule. Code Ocean says journal workflows differ and names only a few integrations (its current guide gives Nature and AACR as examples); do not assume SoftwareX is integrated. [Peer-review guide](https://docs.codeocean.com/osl-guide/publishing-on-code-ocean/peer-review)
2. Import the exact approved source snapshot into the capsule’s `/code`; place only permitted, necessary fixtures/data under `/data`; configure the Python environment; set the root `run` as the run file. Keep passwords and provider credentials out of the repository and capsule files.
3. Commit capsule changes and run once more after any code or data changes. Inspect the complete `/results` output and confirm the manifest names the intended source commit. Code Ocean’s publication checklist requires committed changes and a final Reproducible Run before submission. [Publishing overview](https://docs.codeocean.com/osl-guide/publishing-on-code-ocean/publishing-on-code-ocean-an-overview)
4. Submit through the journal-integrated peer-review route only if the editor confirms it. With an integration, Code Ocean says it sends the private review link to the journal system; without one, the verified capsule is published and the author can provide its DOI. A private capsule URL is only available to its owner/collaborators and is not a public reader link. [Peer-review guide](https://docs.codeocean.com/osl-guide/publishing-on-code-ocean/peer-review) [Link guidance](https://docs.codeocean.com/osl-guide/publishing-on-code-ocean/after-your-capsule-is-accepted-for-publication/which-link-to-my-capsule-should-i-share-with-others)
5. Once published, use the DOI or version-specific published URL (for example, `/tree/vN`) in the manuscript/rebuttal as appropriate. Code Ocean mints the DOI after publication; it identifies a capsule version, and a new published version normally gets a version DOI. Code Ocean documents a metadata-only minor-update exception that keeps the most recent DOI. Record the final capsule version, DOI/URL, and run ID alongside the GitHub commit and Zenodo archive identity. [DOI guidance](https://docs.codeocean.com/osl-guide/publishing-on-code-ocean/after-your-capsule-is-accepted-for-publication/your-compute-capsules-doi) [Version-link guidance](https://docs.codeocean.com/osl-guide/publishing-on-code-ocean/after-your-capsule-is-accepted-for-publication/which-link-to-my-capsule-should-i-share-with-others) [Update guidance](https://docs.codeocean.com/osl-guide/publishing-on-code-ocean/after-your-capsule-is-accepted-for-publication/updating-published-compute-capsules)

## Workflow caveat

Because the DOI is minted only after publication, the authors cannot put the final DOI into the manuscript before that publication step. Resolve with the editor whether the capsule should be submitted as a peer-review copy first or published and then cited; do not put an owner-only private URL where readers are expected to access the capsule. Freeze the code/data snapshot and capsule version before the final GitHub/Zenodo release checks. If only manuscript metadata changes after capsule publication, document that boundary clearly; if capsule code/data changes, rerun and publish the resulting capsule version, then update the cited version identifier.
